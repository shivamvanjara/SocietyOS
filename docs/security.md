# Security notes

This is a development foundation, not a production-ready service. Do not store real resident or financial information in it.

- Environment settings are validated at API startup; secrets belong in environment configuration, never source control.
- The HTTP layer uses Helmet, constrained CORS, a JSON body size limit, and rate limiting.
- Passwords are hashed with Argon2id. Session cookies are HttpOnly, SameSite=Lax, and Secure in production; only SHA-256 session-token hashes are stored. Sessions expire after eight hours and logout revokes them.
- Unsafe browser authentication requests require the configured Origin and a session-bound CSRF token. Login uses a separate IP-based rate limit.
- Society administrators and platform super administrators can enroll an authenticator-based second factor. TOTP secrets are encrypted at rest; production uses a separate required `MFA_ENCRYPTION_KEY`. Login creates a short-lived, single-use pre-authentication challenge in an HttpOnly, SameSite=Strict cookie and issues a session only after code verification. Enrollment and disable actions require password reauthentication plus CSRF; disabling also requires a current TOTP code. Active sessions are revoked on enable/disable except the session performing the action. Active-session management UI and configurable committee permissions remain unimplemented.
- New registrations stay unverified and cannot sign in until a 256-bit verification token is confirmed. Token hashes alone are persisted; links expire after 24 hours and are invalidated when a replacement is requested. Existing accounts are grandfathered as verified during migration.
- Password reset links contain 256-bit random tokens; only SHA-256 hashes are persisted. Tokens expire after 30 minutes, are atomically claimed once, and password changes revoke all active sessions. Production requires transactional email configuration. Local development returns a reset preview link and must not be exposed as a public environment.
- Tenant membership checks, route-level authorization, composite tenant foreign keys, and API integration tests are present. PostgreSQL Row-Level Security is not enabled.
- Platform administration routes require a stored `SUPER_ADMIN` platform role and use CSRF validation for mutations. Society, account, plan, and subscription changes are recorded in platform audit history in the same transaction; account suspension revokes sessions, self-suspension is blocked, and the final active super-admin is protected. Subscription assignments are serialized on the society row and preserve price, interval, and quota snapshots. Configured building and flat quotas are enforced under the same society lock. Recurring subscription collections and feature-based entitlements are not implemented.
- Razorpay orders derive amounts from resident-owned invoices; checkout signatures, provider captured status, raw-body webhook signatures, and duplicate provider events are checked before recording payment. Each society can connect its own merchant credentials; API and webhook secrets are encrypted with a dedicated `RAZORPAY_ACCOUNT_ENCRYPTION_KEY` in production (local development derives a separate key from `SESSION_SECRET`), and payment orders retain a relation to the credential version used when created so rotation does not break pending verification. Society administrators can see only the public key ID; secrets are write-only. Platform subscription billing uses separate platform credentials. Live Razorpay transactions, public webhook delivery, settlement reconciliation, refunds, and an independent security audit have not been verified.
- Production deployment integrations are not present. Expense bill files are limited to 5 MB PDF/PNG/JPEG, signature-checked, and served only to society financial staff. Complaint uploads allow up to five 5 MB JPEG/PNG/WebP images per complaint, signature-checked and accessible only to the submitter and society administrators or committee members. Email verification, password recovery, and society invitations send through Resend when production credentials are configured. Invitation emails contain the one-time token in a URL fragment, and the token is accepted only for the matching invited email address.

Review and test each control when its feature is added. This document is not a security certification.
