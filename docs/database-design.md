# Database design

The schema includes `User`, `Society`, `SocietyMembership`, `SocietyInvitation`, `Session`, `PasswordResetToken`, `EmailVerificationToken`, `Building`, `Flat`, `Resident`, `AuditLog`, `Invoice`, `Payment`, `PaymentOrder`, `SocietyRazorpayAccount`, `PaymentWebhookEvent`, `Expense`, `ExpenseAttachment`, `Notice`, `NoticeRead`, `Complaint`, `ComplaintComment`, `Facility`, `FacilityBooking`, and `VisitorPass`. IDs are PostgreSQL UUIDs except for the provider-issued webhook event key. Membership is unique per society/user pair and carries the society role. Sessions reference a user and store a unique token hash plus expiry. Verification and reset links store token hashes, expiry, and one-time use timestamps; both are cascade-deleted with their user.

Society-owned models carry `society_id`. Composite foreign keys tie flats to same-society buildings, invoices and online payment orders to same-society flats/invoices, payment orders to a same-society Razorpay credential version, payments to same-society invoices, notice reads to same-society notices, and complaint comments to same-society complaints. At most one encrypted society merchant credential version can be active per society; versions remain attached to historical payment orders so key rotations preserve verification. Financial amounts are persisted as integer paise using PostgreSQL `BIGINT`; API inputs accept at most two decimal places and reject overpayments. Invoice period and description uniqueness protects against duplicate charges for the same flat in the same billing period, including concurrent requests. Paid invoices have no update route, and receipts are append-only through the API. Provider payment IDs are unique on payment receipts; webhook events are stored by provider event ID so retries are idempotent. Expenses and financial activity are audited without storing payment amounts or vendor details in audit rows.

Facility bookings reference their facility through a composite society key. Booking overlap checks lock the facility row in the same transaction as the check and create/update operation. Migrations are stored under `apps/api/prisma/migrations`. Apply them with `npm run db:deploy` after configuring `DATABASE_URL`. No PostgreSQL Row-Level Security policies are installed; tenant isolation relies on backend membership checks and relational constraints and must continue to be covered by integration tests.

New expense submissions carry an approval state and submitter/reviewer references. Bill attachments store a validated PDF, PNG, or JPEG as PostgreSQL `BYTEA`, with a database-enforced five-megabyte size limit and same-society composite foreign key.

Complaint image attachments are stored as PostgreSQL `BYTEA` and reference their complaint through a composite `(society_id, complaint_id)` foreign key. The database enforces supported image MIME types and a five-megabyte size limit; the API serializes per-complaint uploads and caps them at five images.

Subscription plans store monthly or annual INR pricing as integer paise and may define maximum building and flat counts. Each society subscription snapshots the plan interval, price, and caps so later plan edits do not rewrite assigned terms. Subscription records reference their society, plan, and assigning platform administrator and are retained when canceled or expired. Platform assignment and reactivation transactions lock the society row to prevent concurrent active subscriptions; building and flat creation use the same lock while checking the applicable caps.

Visitor passes reference same-society flats and store only a hash of the generated one-use code. Check-in updates use a conditional database write so a code cannot be replayed, and entry/exit actors and timestamps remain on the pass record.
